VERIFIED DIAGNOSIS
The request path is benchmark_single_worker.attempt -> controller API ->
run_single_worker/run_two_worker/run_scaling -> HTTP POST through a worker's
Cloudflare tunnel -> worker.diagnostics -> worker.inference.run_inference.
The worker holds one shared GPU lock during synchronous GPU execution.

Previously controller/inference.py:forward and
controller/scaling.py:forward_scaling used timeout=(5,120), independently of
the benchmark's --timeout 135. NN/CNN/GPU diagnostic forwarding did the same.
Their generic requests.Timeout handlers hid whether connection or response
waiting failed. Registry cleanup in finally called finish_nn_test and marked
the worker READY even when the request timed out. This is the verified local
lifecycle defect: an HTTP timeout does not stop the remote GPU operation.

Historical validation_20261010T115546Z_5d593f1c recorded 45 passes in 46
attempts. Row 46 returned the controller-generated HTTP 504 detail in about
5402 ms. Its metadata subsequently recorded a preflight ReadTimeout with
"read timeout=5". Neither event establishes a 120-second GPU execution timeout.

The installed urllib3 HTTPSConnectionPool._make_request sets the connection
timeout before _validate_conn. A socket timeout during HTTPS validation can
be converted to ReadTimeoutError using that connection timeout (5 seconds).
test_https_connect_phase_can_be_reported_as_read_timeout reproduces this
mechanism without networking. This explains how the message is possible
despite a longer read budget. The historical records lack the exception chain
and remote execution logs needed to prove the exact phase or network cause.
No claim is made that Cloudflare itself enforced a five-second deadline or
that the T4 computation failed. Increasing every timeout would not fix the
unsafe READY transition.

CHANGES AND SAFE LIFECYCLE
controller/transport.py:post_execution centralizes single-attempt dispatch.
It sends a unique X-ColabCluster-Request-ID and distinguishes connect_timeout,
read_timeout, generic transport_timeout, connection_error, remote_http_error,
and correlated worker_execution_error. Errors retain a string detail field,
request ID, timeout budgets and bounded remote error text. Remote HTTP 504
remains 504. ConnectTimeout is treated as not_started; ambiguous transport
failures and uncorrelated proxy errors remain unknown. No POST is retried.

worker/diagnostics.py records running/completed/failed execution states under
the shared slot lock. GET /executions/{request_id} reports the worker ID,
request ID, state and slot_available. Reusing a recorded ID returns 409 and
does not execute again. Legacy calls without headers still work and share
the same lock. Worker execution errors carry matching acknowledgement headers.

controller/registry.py retains active reservations and unknown executions.
Unknown executions use status=error plus metadata.execution.state=unknown,
so existing status enums remain compatible and the uncertainty is explicit.
Ordinary READY heartbeats, stale-record expiry and unregister cannot release
these reservations. All diagnostic routes now reserve the same execution slot.
A successful peer in two-worker inference returns to READY independently.

POST /workers/{worker_id}/reconcile performs a read-only worker status query.
Only a matching completed/failed execution with a free slot releases the
reservation. Running, unknown, unreachable, malformed and mismatched replies
keep it unavailable. metadata.execution.observed_remote_state records valid
observations. Reconciliation never resubmits inference or cancels remote work.
It is explicitly invoked, not automatically polled.

LIMITATIONS
This does not guarantee network availability or remotely cancel CUDA threads.
Controller registry and worker execution ledger are process-local. Run one
controller process and one worker server per GPU slot; do not use --workers
or controller --reload during GPU execution. Stop all work before restarts.
An unknown request absent from the ledger is NOT proof it never started; a
delayed request might still arrive. Legacy workers cannot reconcile and must
be redeployed. Do not clear quarantine just by re-registering a worker.
The ledger retains up to 4096 IDs without eviction, then rejects new tracked
work. Restart an idle worker during controlled maintenance before that limit.
If the worker/runtime is lost or a request cannot be reconciled, shut down its
runtime and old tunnel, then restart the controller and workers together so
old delayed requests cannot reach the new execution slot. This is operational
recovery, not automatic cancellation or persistent exactly-once execution.
Live Colab verification remains pending deployment; no live success is claimed.
